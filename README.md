# 反诈协同处置平台

## 启动

本机配置和运行包已准备好时，在项目根目录打开终端，执行：

```powershell
java -jar .\backend\target\antifraud-1.0.0.jar
```

启动完成后打开 <http://127.0.0.1:8088>。服务在当前终端前台运行，用完按 `Ctrl+C` 停止；重启后业务记录仍然保留。Spring Boot 自动读取项目根目录下的 `config/application.properties`。首次克隆请先完成下方的本机配置和构建。

| 角色 | 账号 |
|---|---|
| 中心管理员 | `center` |
| 中心研判员 | `reviewer` |
| 群众 | `public1`、`public2`、`public3`（资金账户户主） |
| 支付机构 | `pay1`、`pay2` |
| 青禾社区网格员 | `grid1`、`grid2` |
| 云栖社区网格员 | `grid3` |

统一演示密码：**`Demo2026!`**。它与数据库密码无关。登录时先选择群众用户、反诈中心、支付机构或社区网格，所选身份须与账号一致。更换角色先退出登录；同一浏览器普通标签页共享会话。

## 演示数据

首次启动空数据库会创建10个课程账号和4个资金账户；重新启动不会清空数据。已有独立演示库及快照继续保留，恢复数据可通过 MySQL 客户端导入快照完成。日常使用只需启动一个服务。

备份和恢复应同时保留数据库、`.local/uploads` 及 `config/application.properties` 中的原应用密钥。应用密钥与已加密记录对应，不能为已有数据库重新生成。恢复演示快照时使用独立数据库，避免覆盖日常业务数据。

## 身份与资金账户

群众登录账号、实名人员、资金账户是三个不同对象。一个已核验群众账号对应一个实名人员；一个人可以有零个或多个资金账户。举报不要求先绑卡。申诉要求申请人为冻结账户的实名户主，返还要求申请人为中心确认的受害人，并选择其本人收款账户。

未实名账号举报后仍可完成首次实名核验，历史举报保留原提交关系；已有业务记录的实名账号不能改绑其他人、移除身份或改换角色。有未完成申请或可重发执行指令时不能停用账号。已经用于派发的账户核验证据不能覆盖，相同材料重复提交不改变复核结果。

冻结资金全部返还后，原止付结束，未决定的返还与申诉申请标为“已失效”并记录原因，未执行的后续指令同步结束；已经作出的核定、裁定和资金流水保留。版本10升级会处理旧数据中相同的未收尾状态，不重新划转资金。申诉已裁定维持时查看原记录，不重复新建同一止付的申诉。

新演示库的关系固定如下（完整账号均为 `622200000000000` 加末位）：

|群众账号|实名主体|本人资金账户|示例用途|
|---|---|---|---|
|public1|居民一|尾号0003|可作为举报提供人，或另一个案件的受害人|
|public2|居民二|尾号0004|下面流程中的受害人，申请返还至本人账户|
|public3|居民三|尾号0001、0002|被止付资金账户户主，可以提出误冻结申诉|

中心管理员可在“实名人员”新增核验资料，在“资金账户”登记账户或补齐旧账户户主，在“账号管理”关联群众的实名身份。群众不能通过自行输入户名或账号占有别人的资金账户。已有核验归属不能直接转给另一人。

号码、网址只是线索，系统没有真实银行或运营商查询接口，不能据此自动查到银行卡或群众账号。中心可看到账号精确匹配或历史核验的候选提示；每个案件仍须填写证据依据，核验线索与账户关系，再完成人工复核。已核验账户的户主来自登记资料，不能从“谁举报”推断。没有查明账户时可先派上门核查。

## 操作顺序

1. `public2` 提交举报，选择“本人受损”：账户 `6222000000000001`、6000元、23:30、异地，可上传 `tests/fixtures/演示材料.txt`。这里填写的是对方涉嫌收款的账户，自己的收款账户在“资金账户”中查看。
2. `center` 打开关联预警，先点“核验关联账户”：选择该举报、尾号0001账户，写明交易凭证等核验依据。随后“人工复核”，确认受害人为居民二、云栖社区，才能联动派发止付和上门任务。
3. `pay1` 受理并提交6000元执行回执；`grid3` 领取任务、记录到场、上传现场材料并回传。`center` 核对两端结果后办结，冻结及后续申请继续独立跟踪。
4. `public2` 申请返还，选择该止付和本人尾号0004收款账户，填写1000元并上传证明。`center` 核定后，`pay1` 受理返还指令并回执。原冻结剩余5000元，尾号0004的余额从600元增至1600元。中心资金对账同时验证转出与入账。
5. `public2` 不能对尾号0001提出户主申诉。退出后用 `public3` 登录，在“返还与申诉”提出误冻结申诉。中心先受理，可要求补正，再作出维持或成立裁定。成立只生成解除指令，由 `pay1` 执行后释放原剩余冻结；已经返还给居民二的1000元不重复退回。
6. 单独验证号码或网址：用“提供线索”提交一个号码/网址，不会自动取得受害人或户主身份。中心确认需要上门的当事人和社区后，可“派发上门核查”，网格回传后办结；或者查明资金账户、核验关联和复核后再联动派发。

“代他人举报”与“提供线索”不自动把登录人当作受害人；中心根据材料核验。举报详情仍归提交者，受害人和账户户主不会因此读取别人的举报附件。申诉材料和返还材料也按各自申请人隔离。

旧版演示快照可能不含这些关系，需要使用新版快照或在独立空库重新准备演示资料。日常业务库升级保留全部记录，不猜测旧账户户主；缺少身份/收款依据的旧未完成申请会失效并保留意见，旧未执行止付缺少账户关联时转中心核验重发。已执行历史资金不改账，真实的新办理须先补齐关系。

## 源码与维护

前端位于 `frontend/src`，后端位于 `backend/src`。技术栈为 Vue 3、Spring Boot、Java 21 和 MySQL 8。本机已构建的 `backend/target/antifraud-1.0.0.jar` 包含前端资源，直接运行不需要另开Vite。Git仓库只保存源码，首次克隆需先构建。

本机重新构建时先停止正在运行的服务，再在项目根目录执行：

```powershell
npm.cmd --prefix frontend ci
npm.cmd --prefix frontend run build
.\backend\mvnw.cmd -B -f backend\pom.xml clean package
```

Maven会直接将`frontend/dist`打入运行包，不需要复制前端文件或执行辅助脚本。构建不需要数据库密码，默认执行Java单元测试；依赖已缓存时可在Maven命令中加`-o`。完成后使用本文开头的`java -jar`命令启动。

`backend/mvnw.cmd`是Maven官方构建工具，仅构建源码时使用，日常启动不需要它。已安装Maven时也可直接执行`mvn -B -f backend/pom.xml clean package`。

## 已做的检查

本轮修复覆盖任务材料权限、止付更正边界、同步超时、宣防截止时间、重复派发、URL匹配、规则溢出、附件清理和旧数据升级。前端附件生命周期测试、后端单元测试以及独立 MySQL 验证库的主线、并发、边界和迁移测试均有相应脚本。

`.github/workflows/ci.yml` 在向 `main` 推送和提交 PR 时执行前端测试及构建、后端测试及完整打包、MySQL 实际接口回归和旧数据迁移检查，测试报告保留7天。CI仅使用临时数据库与自动生成的密钥，不读取任何开发者的本机配置。

本机前端测试执行`npm.cmd --prefix frontend test`；后端测试执行`.\backend\mvnw.cmd -B -f backend\pom.xml test`。接口测试通过 `TEST_BASE_URL` 指定测试实例；SQL边界测试还需 `TEST_DB_NAME`、数据库连接及 `APP_KEY`，仅允许独立的 `antifraud_*verify` 或 `antifraud_*ci` 验证库。`functional_regressions.py`还需要 `APP_LOG` 指向该实例的应用日志，用于核验研判失败时记录了原始异常。综合测试会生成业务数据，不应对日常业务库执行。

此前还完成过四角色29个页面入口、10万条虚构数据及20个独立账号的容量检查、数据库及附件恢复和本机启停验证。这些历史容量结果不代表每次改动都重新跑过压力测试。本机结果保存在 `tests/results`，运行记录不上传Git仓库。

启动失败时先看终端提示和`.local/logs/application.log`，确认MySQL服务已运行、配置文件中的连接信息正确，且8088端口未被其他程序占用。

## 首次从仓库运行

准备JDK 21、Node.js 22.12以上及MySQL 8，设置`JAVA_HOME`并确保`java`、`node`、`npm`可在终端运行。两位开发者各自使用本机的数据库、用户名和密码。

1. 在MySQL中新建utf8mb4数据库和对应用户。
2. 复制配置模板：

   ```powershell
   Copy-Item .\config\application.example.properties .\config\application.properties
   notepad .\config\application.properties
   ```

3. 在配置文件中填写数据库地址、库名、用户名、密码及应用密钥。`server.port`是网页端口；`app.storage`是附件目录。模板里的占位值必须替换。
4. 按“源码与维护”中的三个命令构建，然后执行`java -jar .\backend\target\antifraud-1.0.0.jar`。

仅在为**全新空数据库**首次配置时，可以在PowerShell终端生成32字节Base64应用密钥，将输出填写到`app.key`：

```powershell
$keyBytes = New-Object byte[] 32
$rng = [Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($keyBytes)
[Convert]::ToBase64String($keyBytes)
$rng.Dispose()
```

本机真实配置文件已被Git忽略；仓库只提交不含密码、密钥的模板。队友复制模板填写自己的配置即可，不会覆盖别人的数据库。配置文件中的反斜杠须写成`\\`，路径也可使用正斜杠。已有数据库始终使用其原应用密钥。

## 数据与升级

数据库升级由 `Migrations.java` 按版本执行，成功版本记录在 `af_migration` 中。启动完成升级与基础资料初始化后才开放接口。本轮会保留既有业务记录，将号码、账户及URL的索引升级为由现有应用密钥派生的 HMAC 指纹，同时规范化旧URL。升级前可用MySQL客户端或`mysqldump`备份数据库，并保留附件和本机配置；恢复时必须同时恢复数据和原应用密钥。

网格员可查看本社区待领取任务摘要及本人负责的任务；领取后才能查看居民和材料。回执更正目前支持止付，返还和解除保留原业务流程。宣传活动实际发生时间须在任务创建与截止时间之间，按时完成的活动允许事后登记。未关联材料可由上传人移除，每个账号或匿名会话最多暂存20份、合计50MB，超过24小时的未关联材料由后台清理；已提交材料不参与此清理。

本轮审查补充：群众举报的列表、详情、进度与举报附件统一按提交账号隔离，关联同一受害人不再自动共享举报。匿名凭证查询按连接来源每分钟最多60次，成功与失败均计数，更换会话不会重置配额；当前直连部署不采信客户端的转发IP请求头。举报详情的“管理查询凭证”可重置或停用凭证，旧凭证立即失效。匿名提交响应丢失时，在原提交会话中重试可取回同一受理编号与凭证；切换会话或遗失凭证后需联系中心核验，不提供无凭证找回接口。停用的凭证不会被旧请求重试恢复。

账户管理的“资金对账”独立核查账本连续性、有效回执、冻结余额、累计返还和待执行占用，并列出具体差异，不自动改账。冻结属于可用资金转为冻结资金；当前原型无充值或外部入金，核验关系为“期初余额＋返还入账－返还转出＝可用余额＋剩余冻结”。支付机构只能核验本机构。新库期初值来自初始化配置；旧库优先根据首笔流水反推，缺少流水则取升级时余额，分别标为“历史账本推算”“升级余额基线”，不能据此证明升级之前的记录完全正确。

操作日志的“校验日志”仅供管理员使用。关键日志在同一业务事务中串联带密钥的校验值，并维护链尾和条数；可以发现内容改动、断链、缺失尾部。旧日志在升级时建立校验基线，不能追溯证明此前未改动。这是本库内的篡改检测，不能抵抗同时取得应用密钥并重写整库，或将数据库与链尾一起回滚；不等同于外部只追加审计存储。

URL风险名单按主机、非默认端口与路径匹配，HTTP/HTTPS、查询参数与片段不作为区分项；因此同一路径下不同跳转参数会命中同一条规则，仍需人工复核。域名大小写、IDN、IPv6写法、未保留字符编码、点路径和连续斜杠统一；路径大小写保留，`%2F`等保留分隔符不会直接解码成斜杠，避免把不同路由盲目合并。`UrlRiskTest`明确覆盖这些命中与不命中边界，不声称能识别重定向后的网页内容。

升级时请停止所有连接同一业务库的旧版本实例，并先备份数据库、附件及应用密钥。迁移只移除历史索引 `af_blacklist.kind(kind,value_hash)`；若同名索引结构不同则中止并保留原结构，其他团队自建唯一索引保持不动。失败时不要删除迁移版本号或业务表来强行继续，先核对错误与索引；需回退时使用备份恢复完整数据库和对应附件、密钥，再运行备份时的代码版本。DDL不能保证与数据重算整体回滚，因此不能只回滚代码。已被旧版本迁移删除的未知索引无法自动恢复，应对照升级前备份处理。

`migration_safety.py`额外验证同名异构索引会中止升级、未知索引不会被删除，以及命名锁等待期间接口保持不可用、解锁后才完成初始化。后台业务扫描和附件清理也会等待初始化完成。

新增 `integrity_regressions.py` 使用实际HTTP请求与MySQL行锁重现附件绑定和后台清理重叠，同时验证数据库写入失败后的磁盘清理；`migration_regression.py`逐条检查3000条历史URL跨批迁移、记录数量和额外唯一索引，并记录重启及升级耗时。该规模用于回归，不代表生产数据量的性能保证；现有孤立文件恢复检查也不等同于所有崩溃时刻的故障注入覆盖。

仓库不含 `.local`、数据库口令、业务密钥、上传文件、备份、依赖目录、构建产物和本机测试输出。复制源代码不会带走现有业务数据。

本地演示的身份规则：举报始终属于提交账号；实名人员与登录账号、资金账户分别关联，一个实名人员最多关联一个启用且已核验的群众账号。未核验账号不能绑定实名人员，提交举报自动按匿名线索受理。原止付可由案件受害人或冻结账户户主查看，返还子指令仅向受害人开放，解除子指令仅向户主开放；申请及材料按实际申请账号隔离。旧库若存在重复核验关联，所有冲突账号暂时失去指令、回执和申请权限，但仍可查看各自举报，管理员解除重复关联后恢复。身份更换须先停用或解除原账号关联；新账号经管理员核验关联后按该主体的案件和账户关系办理，历史举报与申请不自动共享。

同来源举报与上传分别限制为每分钟120次，登录每分钟240次；已登录账号举报每分钟60次。登录失败记录保存在有过期时间的限流表中，同账号五分钟8次失败后暂缓登录，过期记录定期清除，不在内存中永久积累随机用户名。默认按直连地址限流，适用于本机演示。

图片在完整解码前检查尺寸（单边不超过10000、总像素不超过2000万），最多同时解码2张，并在解码进度回调中检查耗时；这不是严格的进程级超时隔离。DOCX验证完整ZIP内容，最多1000项、单项解压20MB、合计50MB，并检查处理时间。原有单文件10MB限制保留，不接入外部查毒服务。

合并预警在评分配置与名单版本未变化时只计算新线索，再与原最高分合并；版本变化则重新计算整组线索，保留历史评分记录。重发保留原指令关系，已重发指令不能再次重发或批准旧回执更正；并发业务按统一的身份、预警、指令、资金与审计顺序锁定记录。审计页面分别显示本次校验时间和历史校验链建立时间。

`local_review_regressions.py`覆盖重复身份与未核验权限、匿名重复请求及失败恢复、评分版本变化、重发与更正竞争、资金锁等待期间重复派发、上传解压限制和基本限流。保留本地课程原型的规模：不新增公网部署、验证码、外部审计存储、异步资金队列或大数据量全量对账调度。

功能收尾规则：普通研判员的风险名单详情只读，管理员保留编辑。中心可在“人工待研判”的举报详情中重新研判原记录，恢复后直接查看关联预警。详情连续点击、关闭、切页或切换账号时，过期响应不会覆盖当前页面。派发前更正受害人会同步该预警下全部举报的当前核验身份，保留更正前后日志和原提交账号；派发后仍不能改归属。已闭环、驳回或作废的预警不能重发新的止付，正常返还、申诉及解除继续独立办理。

新止付的派发和失败重发共用人工复核条件：预警处于有效状态、没有待补充复核的线索、最近一次真正的人工复核为通过且对应当前复核人。追加线索待复核、复核驳回或缺少有效复核记录时均返回409，不新增指令或修改原任务；重发理由记录不能替代人工复核。指令详情同步控制重发入口，并提供“前往预警复核”。已有冻结的返还、申诉、解除及这些指令的失败重发继续按原规则办理。首次自动研判失败保留已受理举报，同时按举报ID记录原始异常和调用栈。

联动派发按“同一预警、同一目标账户”检查完整止付历史。已有进行中指令（包括有效重发）时复用原单号；只有该账户从未派发过才新建指令。拒绝或超时后，普通派发返回409并指向最近的失败指令，须从其详情“复核重发”，保留 `retry_of` 关系；已解除的止付也不能通过普通派发重建。其他账户，包括同一机构下的其他账户，仍可独立派发，并共用原上门任务。派发表单区分“新派发”和“复用现有指令”；标为“请复核重发”或“已办理，不再新建”的账户不可选。

普通派发取得预警、指令及资金行锁后，用当前时间同步检查已有指令。冻结到期时先解除冻结、归还余额、清除后续占用并记录账本和审计，再返回409拒绝复用，释放结果不会随这个业务提示回滚；真正的数据库异常仍整体回滚。受理或回执超时则先提交“未处理”及督办记录，再提示从原指令重发。详情中的账户选项也按实际期限判断，即使后台尚未扫描，也不会把已到期或超时指令标为可复用。

审核意见最多2000字，完整保存到申请记录与日志；版本7迁移会将旧库日志说明升级为TEXT，并为新回执更正保存申请时的原回执编号。更正详情并列显示原回执和申请内容，旧更正未保存快照时明确提示。返还申请与中心审核同时显示剩余冻结、待执行占用和当前可核定金额。未知异常对页面显示错误编号，本机日志记录完整调用栈。

`functional_regressions.py`覆盖上述身份更正、原地恢复及异常日志、闭环和补充复核的重发限制、2000字意见、独立返还与解除、更正历史及资金/日志一致性；对拒绝执行和超时两种止付，分别验证复核前拦截、驳回后仍拦截、通过后允许重发，并检查普通派发不能绕过重发链、不同账户可派发、有效重发可复用及两个入口并发时不重复创建。`frontend/tests/detail-loader.test.js`用可控返回顺序验证详情请求竞争，`dispatch-targets.test.js`验证失败账户禁选、重发后复用及其他账户可选。数据库迁移回归同时检查旧日志字段及更正字段升级。

`dispatch_deadline_regressions.py`在用 `--app.commands.scan-enabled=false` 启动的独立测试实例运行，验证普通与延期止付的同步释放、409后事务确实提交、后续占用清理、重复检查不重复入账、资金锁等待中到期、数据库故障回滚，以及未受理/待回执超时。CI已将该测试接在功能回归之后；正常启动默认保留每分钟定时扫描，不使用这个测试开关。

本轮将同样的时效检查覆盖到受理、回执、申请、补正、审核、延期及更正入口；请求排队等待资金行锁时跨过截止点，也不能继续冻结或返还。到期释放会使尚未决定的申请和待审核更正失效，保留已作出的审核决定与全部历史意见；版本8迁移修正旧库中已经结束冻结却仍挂起的申请。前端按后端返回的可办理动作显示按钮，过期原止付不再进入申请选择，状态冲突后刷新详情。

回执更正不能成为绕过复核的第二条路径：拒绝执行改为成功冻结时，申请及批准两次核对预警和补充复核；新增资金依赖、原回执已换版或已到期时拒绝批准。无效金额或执行结果在申请阶段直接拒绝；重新冻结建立新时效周期，避免提醒被旧周期去重。群众补交材料还需保有原受害人的核验关联。

“时效与督办”新增上门任务督办，集中显示超期未回传及劝阻未完成的任务，可打开原任务指定执行人或追加处理说明；正常完成回传或确认异常办结后退出队列。有未完成上门任务的网格员须先交接，不能直接停用或改换角色、社区。“社区宣防”新增中心的“完成 / 取消任务”：完成至少需要一次活动记录；结束停止打卡，保留原记录和时间线。

`lifecycle_regressions.py`新增288步实际接口与MySQL检查，覆盖上述到期、资金锁等待、更正复核、身份变化、任务交接、督办及宣防结束，并已接入CI。本机全套回归、54项Java测试、11项前端测试和3000条历史URL迁移均通过；这些数字是对应脚本的断言及请求步骤数量，不代表全部可能业务组合。

## 身份与资金关系回归

`identity_regressions.py`使用三个不同群众，验证提供线索不自动认定受害人、无绑卡举报、无资金指令的上门闭环、中心核验账户关联及复核、历史关联只作候选、返还与申诉的不同权限、本人收款校验、附件隔离、返还入账、回滚和相反方向的并发返还。`identity_migration.py`在停止独立实例后验证第9版迁移：旧无依据申请失效、取消未执行指令、释放占用、保留已核验新申请、余额和资金流水不变、重复启动不重复处理。

`account_application_regressions.py`补充举报后首次实名、历史身份保护、账户停用、核验证据保护、全额返还后的五种申诉状态、并发补正和失败回滚。`refund_completion_regressions.py`验证两笔600/400元返还分别执行、失败后被其他返还耗尽冻结、失败重发、部分入账、到期与申诉解除，以及失败事务回滚。申请详情分别显示核定金额、实际入账和办理进度。CI随后运行`identity_migration.py`验证第9、10、11版迁移及重复启动，检查原余额、账本和已入账申请不变。

旧测试的正向样例也改用明确的账户核验步骤、本人收款账户，以及独立的户主申诉账号；没有在HTTP客户端里偷偷换人或自动放行账户关系。
